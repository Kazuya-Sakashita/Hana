## 2. Phase ごとの貢献

### Phase A: 画像最適化 (ISSUE-016 / 019 / 018 / 030)

- **取り組み**: BFF cover URL、 Cache-Control、 サムネ style 統一
- **効果**: Speed Index -45% (3 ページ平均) / LCP ほぼ動かず
- **学び**: 画像バイト削減だけでは LCP は動かない (Lighthouse 計測の真の障壁判明)

### ISSUE-031 + Backfill: 画像 variant 事前生成

- **取り組み**: sharp で thumb/preview を upload 時に Storage に保存、 既存 13 件 backfill
- **効果**: 画像合計 Transfer Size **30〜80MB → 1.5MB** (-95% 以上)、 ただし **LCP 元素 = 一部画面でテキスト** と判明
- **学び**: 「LCP killer は画像」 仮説の半分は正しく、 半分はテキスト

### ISSUE-017: requireUser cache

- **取り組み**: React 19 `cache()` + `upsert` → `findUnique/create`
- **効果**: 全 API で -50〜100ms (TTFB 削減、 LCP には間接的)

### Phase B: Server Component 化 + Suspense streaming (ISSUE-026 / 027 / 025)

- **取り組み**: 3 主要ページを async Server Component に、 Suspense で shell streaming
- **効果**: LCP **-26〜46%**、 TBT **-50%** (/album)、 fetch waterfall 解消
- **学び**: 真の LCP killer は **fetch waterfall** で、 SC化が根本解決

## 3. 残る支配要因 (Lighthouse Simulated)

LCP 7.5〜12.7s が依然「Good (< 2.5s)」 に届かない理由:

1. **Lighthouse Simulated Throttling は実体より厳しい**: TTFB / JS execution / image load の全部に倍率がかかる
2. **dev 環境の TTFB**: Next.js dev (Turbopack) は本番より遅い、 Vercel 本番だと半分以下になる見込み
3. **画像 fetch chain**: signed URL の token が dynamic で Vercel cache が効きにくい (将来 SSR cache 課題)

→ **本番 (Vercel) で計測しないと真の性能はわからない**。 dev での数値は「相対的な改善」 を見る目的に限定すべき。
